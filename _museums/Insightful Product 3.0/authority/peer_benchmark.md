> **Status**: Current — reflects Peer Benchmark system with benchmark-framing cleanup applied.
> **Source system**: `SuperCat 4.0/Peer Benchmark/README.md` + `QUERIES.md`
> **Purpose**: Lean guide for how the external report operator consumes peer benchmark output. Not a copy of the Peer Benchmark system spec.
> **Do not duplicate**: The cohort assignment logic, operator architecture, and scoring methodology live in `SuperCat 4.0/Peer Benchmark/`. This file only covers what the external report needs to read and how to use it.

## 1. What Files the External Operator Needs

The Peer Benchmark system produces two output files per run. The external report uses both:

| File | Format | Purpose |
|------|--------|---------|
| `peer_benchmark_YYYY-MM-DD.csv` | Wide — one row per org | Cohort assignment, eligibility flags, and per-metric benchmark columns |
| `peer_benchmark_long_YYYY-MM-DD.csv` | Long — one row per org × metric | Percentile ranks, medians, quartile labels per metric |

Use the most recent run date available. The operator should confirm the file exists and check the `run_date` column before using benchmark data.

**File location**: Peer Benchmark run outputs are generated by `SuperCat 4.0/Peer Benchmark/` operator. Ask the user to confirm which run date to use if multiple are available.

## 2. Required Fields from the Wide Output (`peer_benchmark_YYYY-MM-DD.csv`)

These are the fields the external report operator reads.

### Identity and cohort fields

| Column | Type | Use in Report |
|--------|------|--------------|
| `org_shortname` | string | Entity key — match to current org |
| `org_name` | string | Display name |
| `bundle` | string | Platform stack (e.g., `Full`, `iPad+Catalog+Cart`) |
| `peer_group_id_effective` | string | External-safe cohort label — e.g., `Furniture / Full` |
| `peer_group_level` | string | **Internal only** — `tier1` / `tier2` / `tier3` / `tier4`. Used for gating and caveat calibration. Never surfaces externally. |
| `peer_group_n` | integer | **Internal only** — count of steady-state peers in effective cohort. Used to calibrate framing strength. Never exposed as a literal count in client output. |
| `benchmark_eligible` | boolean | Whether this org qualifies for benchmark |
| `benchmark_confidence` | string | **Internal only** — `high` / `medium` / `low` / `none`. A rendering control signal. Never surfaces as a label in client output. See §5 and §7 for how it governs inclusion and wording. |

### Benchmark metric columns

For each of these metrics, 5 columns are available: `{metric}_org`, `{metric}_peer_median`, `{metric}_pctile`, `{metric}_vs_median`, `{metric}_quartile`.

| Metric | What It Measures | Bundle Gate |
|--------|-----------------|------------|
| `health_score` | Overall Health V2 score | All bundles |
| `value_delivery_score` | Core value realization | All bundles |
| `adoption_score` | Feature breadth / adoption depth | All bundles |
| `engagement_score` | Rep engagement intensity | All bundles |
| `operational_health_score` | Import health, data freshness | All bundles |
| `trajectory_score` | Trend direction (recent vs prior) | All bundles |
| `orders_90d` | Raw order volume | Cart, Full only |
| `orders_per_user` | `orders_90d / total_users` | Cart, Full only |
| `catalog_completeness` | Product data quality ratio | Catalog+ bundles |

**Bundle-gating rule**: For `orders_90d` and `orders_per_user`, check `metric_applicable` in the long format. For orgs on `iPad-only` or `iPad+Catalog`, these metrics are not benchmarked — do not compare.

## 3. How Cohort Assignment Is Used Externally

### How the cohort is described externally

The external report describes the client's peer group using **plain-language framing derived from `peer_group_id_effective`**. The raw label (`{vertical} / {bundle}`) is the internal source value — it informs the framing but is not itself the required output in client prose.

Approved external framing patterns:
- Tier 1 (vertical + bundle match): "Lighting manufacturers on the same platform bundle" (from `Lighting / iPad+Catalog+Portal`)
- Tier 2 fallback (vertical only): "other [vertical] manufacturers" (from `Furniture`)
- Tier 3 fallback (bundle only): "other accounts on the [bundle] plan" (from `Full`)

See §7 for the full list of approved client-facing framing phrases. Do not write the raw `{vertical} / {bundle}` string directly into §7 body prose.

**This is the only cohort context that appears externally.** Internal segment labels (`Platform-Embedded`, `Commerce-Active`, `Catalog-Focused`) must not appear anywhere in the external report — including Peer Benchmarking section prose, headers, or footnotes.

### Where this label appears in the report

The peer group label may appear only in the **Peer Benchmarking section**. It must not appear in:
- The Executive Summary
- Section headers in any other section
- Callout boxes or summary cards outside the Peer Benchmarking section

### Example external-safe framing

> "Compared to your peers — **Furniture manufacturers on the same platform bundle** — your team's engagement is above median, while your order volume sits below the midpoint."

The cohort card in the Peer Benchmarking section should describe the group in plain language like this, not as a raw `{vertical} / {bundle}` label. The gold reference implementation (Crystorama, April 2026) uses: *"Lighting manufacturers on the same platform bundle"* — that is the approved framing pattern.

**`peer_group_n` is an internal calibration signal.** Never expose it as a literal count in client-facing output. Do not write "compared to 33 accounts" or "15-peer cohort" in external prose. Instead, let the `peer_group_id_effective` label carry the cohort description. If a broader context note is needed, use plain-language framing from §7 ("a focused group of similar accounts") — not a number.

## 4. How Percentile and Median Data Is Consumed

### Reading benchmark columns

For each metric from the wide CSV:

```
{metric}_pctile      → 0.0 to 1.0 — percentile rank within effective cohort
{metric}_peer_median → cohort median value
{metric}_vs_median   → signed delta: org value minus cohort median
{metric}_quartile    → Q1 (bottom) / Q2 / Q3 / Q4 (top)
```

### External framing for benchmark standing

| Quartile | Suggested external framing |
|----------|---------------------------|
| Q4 | "Top quartile among your peers" |
| Q3 | "Above median" |
| Q2 | "Below median" |
| Q1 | "Bottom quartile — meaningful gap to median" |

Never use the internal `peer_standing` string values (`Top Performer`, `Commerce Leader`, etc.) as-is — translate into plain language. Never expose percentile rank as a raw decimal — round and contextualize.

### Example from Long Format

Use the long CSV when building narrative metric rows and range bars:

```python
bench_long = pd.read_csv("peer_benchmark_long_YYYY-MM-DD.csv")  # use the current run date
org_rows = bench_long[(bench_long.org_shortname == target_org) & (bench_long.metric_applicable == True)]

for _, row in org_rows.iterrows():
    metric       = row["metric"]
    org_value    = row["org_value"]
    peer_median  = row["peer_median"]
    delta        = row["delta_vs_median"]          # signed: positive = above
    quartile     = row["quartile"]                 # Q1 / Q2 / Q3 / Q4
    pctile       = row["percentile_rank"]          # 0.0–1.0
    p25          = row["peer_p25"]
    p75          = row["peer_p75"]

    # Range bar marker position (clamp to 0–100%)
    if p75 > p25:
        marker_pct = max(0, min(100, (org_value - p25) / (p75 - p25) * 100))
    else:
        marker_pct = 50  # fallback if range is zero

    # Percentile display (readable)
    pctile_pct = round(pctile * 100)
    if pctile >= 0.5:
        pctile_display = f"Top {100 - pctile_pct}%"
    else:
        pctile_display = f"Bottom {pctile_pct}%"
```

### Hero stat selection

The hero stat is the single metric with the most striking story for this org. Selection priority:

1. `orders_per_user` — if `HAS_CART` and `metric_applicable = true`. Most legible to a client: normalized by team size, directly comparable.
2. `engagement_score` — if the org is a strong outlier (Q4 or Q1).
3. `adoption_score` — if Q4 (leads to a positive story about platform depth).
4. `catalog_completeness` — if Q4 or Q1 (either a standout or an actionable gap).
5. `trajectory_score` — if Q3/Q4 and the org's absolute metrics are modest (momentum story).

Never use `health_score` as hero (internal only). Never use a metric where `metric_applicable = false`.

For the percentile display in the hero badge: use `"Top X%"` format for Q3/Q4, `"Bottom X%"` for Q1, absolute value. Round to nearest 5% for cleaner presentation (e.g., 0.67 → "Top 35%", not "Top 33%").

### Sentence writing guide

Write every metric as a complete sentence. Include:
- The org's actual value (formatted — round to 1 decimal, use % for scores)
- The peer median
- The signed delta phrased in plain English
- The peer group in plain-language framing (e.g., "comparable lighting accounts," "Furniture manufacturers on the same platform") — not the raw `peer_group_id_effective` label

Examples by quartile and direction:

**Q4 (above):**
> "Your reps average **23 orders each** in the last 90 days — 64% above the peer median of 14 among Furniture manufacturers on the Full bundle."

**Q3 (above, smaller delta):**
> "Rep engagement score is **71 out of 100**, 8 points above the peer median of 63 — solidly in the upper half of comparable accounts."

**Q2 (below, modest gap):**
> "Catalog completeness is at **74%** — the peer median among comparable Furniture accounts on the same platform is 81%, a 7-point gap worth closing before the next rep training cycle."

**Q1 (below, material gap):**
> "Order volume is **218 in the last 90 days** — the peer median is 412, meaning submission frequency is running below half the midpoint. The orders-per-rep metric tells a more complete story."

Do not use hedging language ("somewhat," "slightly") — use the actual numbers. Do not write in the passive voice. Do not apologize for a Q1 or Q2 standing.

## 5. Gating Logic for the Peer Benchmarking Section

`benchmark_confidence` is an **internal rendering/control signal** only. It is never displayed as a label in client-facing output. Use it to decide whether to include the section and which caveat language to use — not to create a visible "confidence rating" for the client.

| Condition | Action |
|-----------|--------|
| Peer benchmark file not available | Omit Peer Benchmarking section entirely. Omit from TOC. No note in delivered report. |
| `benchmark_eligible = false` | Omit Peer Benchmarking section. Omit from TOC. No note in delivered report. Do not create a blank section. |
| `peer_group_level = 'tier4'` | Omit Peer Benchmarking section. Omit from TOC. No note in delivered report. No viable cohort — do not show empty comparison. |
| `benchmark_confidence = 'low'` | Include section with plain-language directional framing. `low` reflects Tier 2/3 fallback cohort or a ramping org — it is not a simple "weak data" signal. Use §7 caveat language appropriate for the tier. Do not expose the `low` label. Do not block the section. |
| `benchmark_confidence = 'medium'` | Include with a brief directional note in plain language. `medium` reflects a Tier 1 cohort at the lower end of the stable-peer threshold (5–7 peers). Do not expose the `medium` label. Use §7 language. |
| `benchmark_confidence = 'high'` | Include without caveat. `high` reflects a well-populated Tier 1 cohort (≥8 steady-state peers). No label needed. |

**Peer Benchmarking is always included when an eligible peer group exists.** The reference HTML accidentally omitted the Peer Benchmarking section — this was not an editorial cut and must not be treated as precedent.

### What `benchmark_confidence` actually reflects

The signal blends two distinct factors:
1. **Cohort specificity / fallback level** — whether the org landed in a specific Tier 1 vertical+bundle cohort or fell back to a broader Tier 2/3 grouping
2. **Peer set stability** — whether the steady-state peer count is large enough for stable percentile ranks

These two factors produce the same `low` label for different underlying reasons. A Tier 3 cohort with n=50 (iPad-only plan) and a Tier 1 cohort with n=3 (niche vertical) both generate `low` — but the interpretation differs. Use `peer_group_level` and `peer_group_n` together with `benchmark_confidence` to calibrate the specific plain-language framing. Do not read `low < medium < high` as a simple linear quality ranking — `medium` is not always "better data" than `low` in every meaningful sense.

### Interpreting `peer_group_n` vs. assigned cohort size

`peer_group_n` counts only **steady-state peers** — orgs that are fully onboarded and not in a ramping period. Ramping/onboarding orgs are assigned to a cohort for their own scoring but excluded from being counted as peers. This means:

- An org may be assigned to a cohort with a visible label (e.g., `Furniture / Full`) but `peer_group_n` reflects only the stable comparison population
- If `peer_group_n` looks smaller than expected given the cohort label, this is expected behavior — not a data gap
- Do not infer from a small `peer_group_n` alone that the cohort is untrustworthy; check `benchmark_confidence` as the authoritative signal

### Tier 3 is not automatically a limitation

A `peer_group_level = 'tier3'` (bundle-only cohort) is not a failure state. It means no vertical-level cohort was large enough, but the bundle-level comparison is still valid and meaningful. Frame Tier 3 as an honest cohort descriptor, not as a caveat that the benchmark is weak.

- **Only omit Peer Benchmarking if `peer_group_level = 'tier4'`** (no viable cohort at any level)
- For Tier 3: use the Tier 3 fallback framing and `benchmark_confidence` to calibrate caveat language — confidence level governs the caveat, not the tier alone

## 7. Client-Facing Benchmark Language

These labels are **for internal use only** — they must never appear in client-facing output:
- `high confidence` / `medium confidence` / `low confidence`
- `tier1` / `tier2` / `tier3` / `tier4`
- `peer_group_n` as a literal count — **never expose as a number in client-facing output**
- `benchmark_confidence` value in any form
- `steady-state peers` or similar internal vocabulary describing the peer-count methodology

### Upstream signal reference (internal)

| `benchmark_confidence` | What drives it |
|---|---|
| `high` | Tier 1 cohort with ≥ 8 steady-state peers |
| `medium` | Tier 1 cohort with 5–7 steady-state peers |
| `low` | Tier 2 or Tier 3 fallback cohort, OR ramping/onboarding org (regardless of `peer_group_n`) |
| `none` | Tier 4 — no viable cohort; section must be omitted |

**Important**: `low` does not mean a small raw peer count. A Tier 3 bundle-only cohort may have a large `peer_group_n` — e.g., the iPad-only Tier 3 cohort has n=50. The signal reflects cohort specificity and fallback level, not peer count alone. Use `peer_group_n` to assess statistical reliability and calibrate phrasing weight; use `benchmark_confidence` to decide whether a plain-language context note is needed at all.

### Plain-language framing to use externally

When `benchmark_confidence` is `low` (Tier 2/3 fallback or ramping org), use directional framing:
> "These comparisons are drawn from a broader peer set — accounts across your industry segment on a similar plan. Use them as directional context."
> *(When n is also small: "These benchmarks are based on a focused comparison group. Treat specific values as directional rather than precise.")*

When `benchmark_confidence` is `medium` (Tier 1, moderate peer count):
> "These comparisons are drawn from a focused group of similar accounts on the same platform bundle. Trends are meaningful; point-in-time figures should be read directionally."

When `benchmark_confidence` is `high` (Tier 1, well-populated):
No caveat needed. Write benchmark observations directly in plain language.

**Tier 2 fallback (vertical only, no bundle match) — plain framing:**
> "Your comparison group is made up of other **[vertical]** manufacturers. Platform-specific segmentation was not available at this cohort size, so comparisons reflect your broader industry context."

**Tier 3 fallback (bundle only, no vertical match) — plain framing:**
> "Your comparison group is made up of other accounts on the **[bundle]** plan. These are valid benchmarks — platform-level usage patterns are directly comparable across this group."

Do not frame Tier 3 as a limitation or apology. It is a valid comparison set. Only add a caveat when `benchmark_confidence` is also `low` or `medium` and the framing benefit outweighs the risk of making the client feel the benchmark is unreliable.
