# Craft CMS Formatting Guidelines v2.0

**Purpose:** Universal formatting rules for all KB article content generated for Craft CMS.

**Version:** 2.0  
**Updated:** January 18, 2026  
**Changes from v1.0:** Added Article Type Classification, type-specific templates, step format options, section consolidation rules, structured label patterns, and image placeholder guidance.

## 📝 Validation & Audit Trail

**All validation notes, changes, and revision history go at the TOP of the Notion page. Do NOT create separate files.**

When updating or creating a Craft draft, add a revision block at the top of the Notion page:

```markdown
# REVISED CRAFT UPDATE
**Date:** [Date]
**Craft Draft URL:** [URL]
**Entry ID:** [ID]

## Changes Made in This Revision
1. ✅ [Change 1]
2. ✅ [Change 2]
...

## Image Requirements (if applicable)
| Section | Image Description | Source |
|---------|------------------|--------|

## Complete Draft Content
[Full article content below]
```

**Why at the TOP:** Maintains audit trail with newest revisions first. Kyla can review changes before publishing.

## ⭐ START HERE: Article Type Classification

Before applying formatting rules, identify your article type. Different types require different structures.

### Step 1: What is the primary purpose?

| If the article... | Then it's a... |
|-------------------|----------------|
| Helps users fix an error or problem they're experiencing | **Troubleshooting Guide** |
| Explains what a feature is AND how to set it up | **Feature Overview + Setup Guide** |
| Walks users through completing a specific task | **How-To Guide** |
| Documents multiple related errors, settings, or options | **Reference Guide** |

### Step 2: Secondary considerations

| Question | If Yes... |
|----------|-----------|
| Does the task vary by user type or platform? | Use **Multi-Path How-To** structure |
| Is this a complex feature requiring prerequisites? | Use **Feature Overview** structure |
| Are there 4+ parallel items (errors, settings, options)? | Use **Reference Guide** structure |
| Is it a single, simple task? | Use **Simple How-To** structure |

### Step 3: Apply the matching template below

## Article Type Templates

### Template A: Troubleshooting Guide

**Use when:** User is experiencing an error, problem, or unexpected behavior.

**Pattern:** Problem Statement → Why It Happens → How to Identify → How to Fix → Still Having Issues? → Prevention

**Example:** [Fixing Invalid URLs in Custom Enrollment Email Templates](https://supercatsolutions.com/knowledgebase/fixing-invalid-urls-in-custom-enrollment-email-templates)

**Required sections:**
```
H2: [Descriptive intro paragraph - state the problem]
H2: Why This Happens
H2: How to Identify the Issue
H2: How to Fix / What You Can Do
H2: Still Seeing the Error? (optional - for edge cases)
H2: Prevention
H2: Troubleshooting (if additional FAQs needed)
```

**Intro approach:** Open by describing the **symptom** users experience.
> "When recipients click the enrollment link, they may land on an invalid or broken URL..."

**Step format:** Numbered list or H3 steps (limited count, typically 5-8 main steps).

---

### Template B: Feature Overview + Setup Guide

**Use when:** User needs to understand what a feature does before they can use it. Common for complex features requiring configuration.

**Pattern:** Summary → What Is It → How It Works → Access/Permissions → Prerequisites → Setup Steps

**Example:** [Option Mapping](https://supercatsolutions.com/knowledgebase/option-mapping)

**Required sections:**
```
H2: Summary (1-2 paragraphs: what it does, who it's for)
H2: Overview
    H3: What Is [Feature Name]?
    H3: How It Works
H2: Access & Permissions (optional - for admin features)
H2: Prerequisites / Before You Begin
H2: How to [Set Up / Configure / Use] [Feature Name]
H2: Troubleshooting
```

**Intro approach:** Open with a **Summary** explaining what the feature does.
> "The Option Mapping feature gives admin users the ability to define relationships between product options..."

**Step format:** H3 steps for the main setup procedure. Prerequisites as numbered list.

**Key characteristics:**
- Conceptual explanation comes BEFORE procedural steps
- Prerequisites section BEFORE the how-to
- May include Access/Permissions for admin-only features
- Tip blockquotes for helpful hints

---

### Template C: How-To Guide (Multi-Path)

**Use when:** Users need to complete the same task but steps vary by user type, platform, or scenario.

**Pattern:** Overview → [Path A] → [Path B] → [Path C]

**Example:** [Updating Account Email](https://supercatsolutions.com/knowledgebase/updating-account-email)

**Required sections:**
```
H2: Overview (brief intro, list the different paths)
H2: [User Type A / Platform A]
H2: [User Type B / Platform B]
H2: [User Type C / Platform C]
H2: Troubleshooting (optional - if common issues exist)
```

**Intro approach:** Brief statement of **what they'll accomplish**, then list the paths.
> "You can update your account email from any eCat platform. Choose your platform below:"

**Step format:** Bullet lists under each path's H2 (steps may vary slightly between paths).

**Key characteristics:**
- Parallel structure across paths
- Each path is self-contained
- Very task-focused, minimal explanation
- Often no troubleshooting needed (simple tasks)

---

### Template D: How-To Guide (Simple/Single Path)

**Use when:** Single focused task with straightforward steps.

**Pattern:** Overview → Steps → Done

**Example:** [Scan Items to Lists](https://supercatsolutions.com/knowledgebase/scan-items-to-lists)

**Required sections:**
```
H2: [Task Name] (steps directly follow)
```

**Intro approach:** One sentence stating what the user will do.

**Step format:** Numbered list or bullet list.

**Key characteristics:**
- Very short
- Single use case
- No troubleshooting needed
- Minimal sections

---

### Template E: Reference Guide (Multiple Parallel Sections)

**Use when:** Documenting multiple related items (error types, settings, configuration options) that share the same internal structure.

**Pattern:** Overview → [Item 1] → [Item 2] → ... → Best Practices → Troubleshooting → Contact Support

**Example:** Understanding Image Errors in SuperCat

**Required sections:**
```
H2: Overview (list all items covered)
H2: [Item Type 1: Name]
H2: [Item Type 2: Name]
... (repeat for each item)
H2: Best Practices
H2: Troubleshooting
H2: Contact Support (standalone for comprehensive guides)
```

**Intro approach:** List all items covered in the guide.
> "This guide covers the seven most frequent image-related errors..."

**Step format:** **Ordered lists** (`<ol>`) for steps within each item section. This keeps TOC clean.

**Internal structure for each item section:**
```html
<h2>Error Type 1: Missing Image File</h2>
<p><strong>What This Error Means:</strong> Description here.</p>
<p><strong>Root Cause:</strong> Explanation here.</p>
<p><strong>Error Messages:</strong></p>
<ul>
<li>Error message 1</li>
<li>Error message 2</li>
</ul>
<p><strong>How to Fix:</strong></p>
<ol>
<li>Step one explanation.</li>
<li>Step two explanation.</li>
<li>Step three explanation.</li>
</ol>
```

**Key characteristics:**
- Multiple parallel sections with **identical internal structure**
- Use ordered lists for steps (NOT H3 headings) to prevent TOC bloat
- Consistent label formatting across all parallel sections
- Standalone "Contact Support" section at bottom (for guides with 8+ sections)

## Terminology Consistency

### The Core Rule

**The existing Craft article's terminology is authoritative.** When merging or updating content, maintain consistency with the published article's naming conventions.

### Why This Matters

- **SEO:** Users searching for "Grade Jump Riser Pricing" should find content using that exact phrase
- **Brand consistency:** Avoids confusing users who might think different terms refer to different features
- **Searchability:** Consistent terminology improves internal KB search results

### Terminology Patterns

| Context | What to Use | Example |
|---------|-------------|---------|
| **Title / Feature name** | Full official name from Craft | "Grade Jump Riser Pricing" |
| **First reference in body** | Full name, optionally noting short form | "Grade Jump Riser Pricing (also called riser pricing)" |
| **Subsequent body references** | Short form is acceptable if Craft uses it | "riser pricing" |
| **Field names** | Exact casing from codebase | 'DiscountPriceLevelCode' not "discount price level code" |

### When Notion Uses Different Terminology

1. **Default action:** Standardize to Craft's terminology in the merged/prepared content
2. **If Notion term seems more accurate** (e.g., reflects a product rename): Flag for review, don't auto-change
3. **Always document:** List terminology standardizations in output

### Common Terminology Mismatches to Watch For

| Type | Example Mismatch | Resolution |
|------|------------------|------------|
| Full vs. short name | "Grade Jump Riser Pricing" vs. "riser pricing" | Use full name in title, short form acceptable in body |
| Formal vs. casual | "Special Promotion Pricing" vs. "promo pricing" | Use formal name, allow casual in body if Craft does |
| Technical vs. user-friendly | 'DiscountPriceLevelCode' vs. "discount field" | Use technical term in single quotes, can explain in plain language |

## Bold Text Usage (Use Sparingly)

### DO Bold:
- **Navigation paths:** `Admin Console > Section > Page`
- **UI elements** (buttons, menus, tabs): Click **Save**, tap **Actions**, select **Settings**
- **List item titles/labels:** "**Option A:** Description here..."
- **Step headings:** "**1. Step Name**"
- **Structured labels:** "**What This Error Means:**", "**Root Cause:**"

### DO NOT Bold:
- General descriptive text or explanations
- Emphasis words that aren't UI elements or field references
- Common nouns or phrases within sentences

> **Rule of thumb:** If a user wouldn't click it or type it, don't bold it.

---

## Field Names & Technical Terms

Use **single quotes** for field names and file names in running prose:
- Field names: 'FieldName', 'CollectionCodes', 'CategoryCodes'
- File names: 'products.csv', 'option_groups.csv'

Use `inline code` formatting only for:
- Actual code snippets or commands
- API endpoints or system paths
- Values the user will type or copy exactly

**Always verify field names** against the codebase or import documentation - use exact casing.

### Examples:
| Correct | Incorrect |
|---------|-----------|
| the 'MappedBillToCode' field | the `MappedBillToCode` field |
| your 'customer.csv' file | your `customer.csv` file |
| add the 'GradeJumpRiserCount' column | add the `GradeJumpRiserCount` column |
| populate 'CollectionCodes' and 'CategoryCodes' | populate `CollectionCodes` and `CategoryCodes` |

## Notes, Tips, and Warnings

Always use **blockquote format** with appropriate prefix:

### Note (informational context)
```html
<blockquote><strong>Note:</strong> Informational context here.</blockquote>
```

### Tip (helpful suggestion)
```html
<blockquote>💡 <strong>Tip:</strong> Helpful suggestion or shortcut here.</blockquote>
```

### Important/Warning (critical information)
```html
<blockquote>⚠️ <strong>Important:</strong> Critical information or warning here.</blockquote>
```

**Placement:** Callouts should appear immediately after the relevant content, not buried within bullet lists.

## Step-by-Step Structure

### Choose Your Step Format Based on Article Type

| Article Type | Recommended Step Format | Why |
|--------------|------------------------|-----|
| How-To Guide (primary focus is steps) | H3 numbered headings | Steps are main content, TOC visibility helpful |
| Feature Overview (steps are one section) | H3 numbered headings | Limited steps, TOC sub-entries acceptable |
| Reference Guide (steps in multiple sections) | **Ordered lists** `<ol>` | Prevents TOC bloat from repeated step sequences |
| Multi-Path How-To | Bullet lists | Steps vary slightly between paths |
| Troubleshooting Guide | Numbered list or H3 | Depends on step count |

### Format A: H3 Step Headings (for How-To and Feature Overview)

```html
<h3>1. Step Name</h3>
<p>Explanation of what this step accomplishes and how to do it.</p>

<h3>2. Next Step</h3>
<p>Continue with the next action.</p>
```

**Use when:** Steps are the primary content and you have 3-8 main steps.

### Format B: Ordered Lists (for Reference Guides)

```html
<p><strong>How to Fix:</strong></p>
<ol>
<li>First step explanation here.</li>
<li>Second step explanation here.</li>
<li>Third step explanation here.</li>
</ol>
```

**Use when:** You have multiple parallel sections each containing steps (e.g., 7 error types each with "How to Fix" steps). Keeps TOC clean.

### Format C: Bold Paragraph Steps (for steps that shouldn't be in TOC)

```html
<p><strong>1. Review and Match</strong></p>
<p>For each unique UUID, decide if it is new or duplicate.</p>

<p><strong>2. Update Your File</strong></p>
<p>Locate the matching record and update the field.</p>
```

**Use when:** Steps are secondary content within a larger section and shouldn't appear in TOC.

### General Rules:
- **One step = one primary action**
- Place explanation as a **regular paragraph directly below** the step
- Use short bullet lists only for discrete sub-items within a step

### Good Example:
```html
<h3>1. Review and Match</h3>
<p>For each unique UUID, decide if it is a new customer or a duplicate of an existing one.</p>

<h3>2. Update Your Customer File</h3>
<p>Locate the matching official customer record in your 'customer.csv' file. Copy the 'LocalCustomerCode' (UUID) into the 'MappedBillToCode' field for that customer.</p>
<blockquote>⚠️ <strong>Important:</strong> Do not overwrite the 'BillToCode' field. The 'MappedBillToCode' is a separate field.</blockquote>
```

### Bad Example (Avoid):
```html
<ol>
  <li><strong>Review and Match:</strong>
    <ul>
      <li>For each unique UUID, decide if it is a new customer...</li>
    </ul>
  </li>
</ol>
```
This nested structure creates visual disconnect and is harder to scan.

## Structured Label Patterns

**Use for:** Reference Guides and articles with repeated content blocks that share the same internal structure.

### Standard Labels by Content Type

**For Error/Issue Descriptions:**
```html
<p><strong>What This Error Means:</strong> Description of the error.</p>
<p><strong>Root Cause:</strong> Why this happens.</p>
<p><strong>Error Messages:</strong></p>
<ul>
<li>Error message text 1</li>
<li>Error message text 2</li>
</ul>
<p><strong>How to Fix:</strong></p>
<ol>
<li>Step one.</li>
<li>Step two.</li>
</ol>
```

**For Feature/Setting Descriptions:**
```html
<p><strong>What It Does:</strong> Description of functionality.</p>
<p><strong>When to Use:</strong> Use cases or scenarios.</p>
<p><strong>How to Configure:</strong></p>
<ol>
<li>Step one.</li>
<li>Step two.</li>
</ol>
```

**For Comparison Items:**
```html
<p><strong>Description:</strong> What this option does.</p>
<p><strong>Best For:</strong> When to choose this option.</p>
<p><strong>Limitations:</strong> What it doesn't do.</p>
```

### Consistency Rule

**All parallel sections must use identical label structure.** If Section 1 uses "What This Error Means:", then Sections 2-7 must also use "What This Error Means:" (not "What This Means:" or "Error Description:").

## Typography Rules

### No Em-Dashes
**Do NOT use em-dashes (—) in any KB article content.**

| Instead of... | Use... |
|---------------|--------|
| "Click Save — this saves your changes" | "Click Save. This saves your changes." |
| "The feature — which is optional — can be enabled" | "The feature (which is optional) can be enabled" |
| "Step 1 — Review the data" | "Step 1: Review the data" |

**Alternatives to em-dashes:**
- Use a period and start a new sentence
- Use parentheses for asides
- Use a colon for explanations
- Use a comma if grammatically appropriate

---

## Structural Rules

### Avoid:
- **Em-dashes (—)**: use periods, colons, or parentheses instead
- **Nested bullet structures** like "1. **Title:** \n - explanation"
- **Italics-only** for important information (too easy to miss)
- **Mixed numbering** systems (1, 2, 3 then a, b, c)
- **Deeply nested content** (max 2 levels of indentation)

### Prefer:
- Flat structure with clear headings
- Paragraphs for explanations
- Bullets only for truly list-worthy items (options, features, requirements)
- Tables for comparisons or reference data

## Table of Contents (Auto-Generated)

Craft auto-generates the TOC from H2 and H3 headings. Keep it clean:

### Section Naming
- **Short titles:** "Merging Local Customers" not "Part 3: Merging Local Customers into Your Master Database"
- **No "Part X:" prefixes**: just clear, scannable titles
- **No numbering in H2 titles**: let the TOC add numbers

### Controlling TOC Depth
- **H2** = Main TOC entries (always)
- **H3** = Sub-entries (use sparingly, only if truly needed for navigation)
- **Bold text in paragraphs** = Steps that should NOT appear in TOC
- **Ordered lists** = Steps that should NOT appear in TOC (preferred for Reference Guides)

```html
<!-- This creates TOC sub-entries (often too much): -->
<h3>1. Review and Match</h3>

<!-- This keeps steps OUT of TOC (usually better): -->
<p><strong>1. Review and Match</strong></p>
<p>For each unique UUID, decide if it is new or duplicate.</p>

<!-- This also keeps steps OUT of TOC (best for Reference Guides): -->
<ol>
<li>Review and match each UUID.</li>
<li>Update your file accordingly.</li>
</ol>
```

### Ideal TOC Length by Article Type

| Article Type | Target TOC Entries | Notes |
|--------------|-------------------|-------|
| Simple How-To | 3-5 | Minimal sections |
| Feature Overview | 6-10 | Includes sub-sections |
| Troubleshooting Guide | 5-8 | Problem → Solution flow |
| Reference Guide | 8-15 | One entry per item + standard sections |

**Avoid:** 15+ entries or deep nesting (makes TOC overwhelming)

## Section-Specific Rules

### Related Articles
**Do NOT include a Related Articles section** - Craft automatically generates related articles at the bottom of each page.

### Summary Section
**Do NOT include a separate Summary section** - Merge summary content into the Overview section at the top. A Summary at the end is redundant.

### Prerequisites / Before You Begin

**Placement depends on article type:**

| Article Type | Prerequisites Placement |
|--------------|------------------------|
| Feature Overview + Setup | Dedicated H2 section BEFORE the how-to steps |
| How-To Guide | Brief bullets at top of article OR omit if none |
| Reference Guide | Usually not needed |
| Troubleshooting Guide | Usually not needed |

**Format:**
- Keep brief (3-5 bullet points max)
- Link to other articles rather than explaining prerequisites in detail

### Best Practices / Prevention

**Consolidate into ONE section called "Best Practices".**

**DO NOT create separate sections for:**
- ❌ Prevention Tips
- ❌ Tips & Tricks
- ❌ Recommendations

**DO:**
- ✅ Combine all preventive/best practice content into one "Best Practices" section
- ✅ Use bold labels for categories (File Naming, File Preparation, Import Process)
- ✅ Use bullet lists for individual tips

### Troubleshooting (SINGLE SECTION)

**CRITICAL:** All troubleshooting-related content goes in ONE section called "Troubleshooting". 

**DO NOT create separate sections for:**
- ❌ FAQs
- ❌ Common Mistakes
- ❌ Common Issues
- ❌ Need Help?
- ❌ Support / Contact (exception: see Contact Support below)

**DO:**
- ✅ Combine all of the above into one "Troubleshooting" section
- ✅ Use bold question format for each issue
- ✅ Keep answers concise and direct

**Format:**
```html
<h2>Troubleshooting</h2>

<p><strong>Question or issue here?</strong><br>
Direct answer here.</p>

<p><strong>Another common question?</strong><br>
Answer here.</p>
```

### Contact Support

**Placement depends on article length:**

| Article Length | Contact Support Placement |
|----------------|--------------------------|
| Short (< 8 sections) | Final paragraph within Troubleshooting section |
| Long/Comprehensive (8+ sections) | **Standalone H2 section** at the very end |

**Short article format (within Troubleshooting):**
```html
<p><strong>Need more help?</strong><br>
<a href="mailto:support@supercatsolutions.com">Contact Support</a>. We'll walk through your setup.</p>
```

**Long article format (standalone section):**
```html
<h2>Contact Support</h2>
<p>If you continue to experience issues after following the steps above, our support team is here to help.</p>
<p><a href="mailto:support@supercatsolutions.com">Contact Support</a> with:</p>
<ul>
<li>Specific error messages</li>
<li>Steps you've already tried</li>
<li>Screenshots (if possible)</li>
</ul>
```

## Image Placeholder Documentation

**Use when:** Images need to be added manually after draft creation (images cannot be added via GraphQL).

**⚠️ CRITICAL: Maximum 3 image placeholders per article.** If you need more, prioritize the most impactful.

### In-Article Placeholders

Use this UNMISTAKABLE format so Kyla knows to replace or remove before publishing:

```html
<p><strong>⚠️ [PLACEHOLDER - DO NOT PUBLISH] Screenshot needed:</strong> <em>Description of the needed screenshot or image.</em></p>
```

**Examples:**
```html
<p><strong>⚠️ [PLACEHOLDER - DO NOT PUBLISH] Screenshot needed:</strong> <em>Missing Images report download location showing the Download button.</em></p>
```

**Why this format:**
- The ⚠️ emoji and bold text make it visually obvious
- "[PLACEHOLDER - DO NOT PUBLISH]" is impossible to miss in preview
- Kyla can search for "PLACEHOLDER" to find all items needing attention

### Image Requirements Documentation

**Document image requirements at the TOP of the Notion page** (in the validation/revision notes section), NOT in a separate file:

```markdown
### Image Requirements
| Section | Image Description | Source |
|---------|------------------|--------|
| Error Type 1 | Missing Images report download location | Help Scout ticket |
| How to Fix | Admin Console navigation screenshot | Create in staging |
```

### Image Limits

- **Maximum:** 3 images per article (prioritize most impactful)
- **Priority order:** 
  1. Most common issue/use case
  2. Complex navigation that's hard to describe
  3. Before/after comparisons

## Quick Reference

| Element | Format |
|---------|--------|
| Feature name (title) | Use Craft article's official name |
| First body reference | Full name, optionally: "Feature Name (also called short name)" |
| Subsequent references | Short form acceptable if Craft uses it |
| Navigation path | **Admin > Section > Page** |
| Button/UI click | **Save**, **Actions**, **Settings** |
| Field name | 'FieldName' (single quotes, exact casing) |
| File name | 'filename.csv' (single quotes) |
| Note | `<blockquote><strong>Note:</strong> text</blockquote>` |
| Tip | `<blockquote>💡 <strong>Tip:</strong> text</blockquote>` |
| Warning | `<blockquote>⚠️ <strong>Important:</strong> text</blockquote>` |
| Step heading (How-To) | `<h3>1. Step Name</h3>` |
| Step list (Reference Guide) | `<ol><li>Step text</li></ol>` |
| Structured label | `<p><strong>Label:</strong> text</p>` |
| Image placeholder | `<p><strong>⚠️ [PLACEHOLDER - DO NOT PUBLISH] Screenshot needed:</strong> <em>Description.</em></p>` |
| Troubleshooting | ONE section combining FAQs, mistakes, issues |
| Best Practices | ONE section combining tips, prevention |
| Contact Support | Within Troubleshooting (short) OR standalone H2 (long) |
| Related Articles | ❌ Don't include (Craft auto-generates) |
| Summary | ❌ Merge into Overview, don't create separate section |
| Em-dashes (—) | ❌ Don't use. Use periods, colons, or parentheses instead |
