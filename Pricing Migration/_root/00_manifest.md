6. **Echo every `_root/` doc title + last-updated date in your first chat response** (the manifest-echo contract per `_root/CONTRACTS.md §2`). Use the table in §2 of this manifest as the authoritative list. If a date you read in a doc's header disagrees with this manifest, that is a §3-propagation failure (QB-125 in `_root/08`); stop and flag.

## §5. Conformance-block format (canonical, replaces per-prompt specifications)

`_root/CONTRACTS.md §verifying-conformance` step 3 reserved this format's ownership for `_root/08`, then deferred the canonical specification to this manifest. As of 2026-05-22 (Stage 5), the canonical conformance-block format is below. Every fresh-agent session ends with this block in its final chat message.

```
─── Conformance Block ─────────────────────────────────────────
Session task: <one-line description of what this session was asked to produce>
Output target: <file path(s) written, OR "no files written; analysis only">

Files read (with last-updated date / mtime):
- <path 1> — <last-updated date from header, or filesystem mtime>
- <path 2> — <same>
- ...

Explicitly-authorized archive reads (only if the prompt opened this exception per CONTRACTS §4):
- <archive path> — <which prompt section authorized; what was extracted>
- <or: "none">

Files NOT read (per the task scope / "Do NOT read" list):
- <path or scope>
- <or: "none beyond default scope">

[Task-specific counts — vary by task. Per-account briefs include format selected, driver block used (§N.M reference), QB-NNN pass/fail/N/A list. _root/ doc authoring sessions include section counts and rule extractions. QA-only audit sessions include the brief audited + QB-NNN results.]

Gaps surfaced (a rule in _root/ with no check / no extraction path, OR a piece of source material with no _root/ home):
- <gap with explanation>
- <or: "none">

Conflicts between sources (where two sources disagreed and I had to pick or flag):
- <conflict with chosen resolution>
- <or: "none">

Open questions for operator:
- <question with the specific decision needed>
- <or: "none">
─────────────────────────────────────────────────────────────
```

Severity-level enforcement for the conformance block itself:

- **The block is mandatory.** A session without one is a `_root/CONTRACTS.md §2` failure (QB-002 in `_root/08`).
- **Every section heading above is mandatory.** A section may be empty (e.g. "Open questions for operator: none"), but missing the heading entirely is a structural failure (QB-002 + QB-003).
- **The files-read list must be complete.** Every file the session opened with a tool call appears in the list, with its last-updated date or mtime. Missing entries are a `_root/CONTRACTS.md §verifying-conformance` step 1 failure (QB-003).
- **Open questions for operator must be substantive.** An open question that does not name the specific decision needed is non-actionable; the operator either treats it as "none" or escalates as a conformance-block-format failure.

Per-task variation in the "[Task-specific counts]" block is acceptable and expected — a Stage 4 brief draft surfaces different counts than a Stage 2 `_root/` author session. The four constant elements — files read, files not read, gaps, conflicts, open questions — are non-negotiable across every task type.
