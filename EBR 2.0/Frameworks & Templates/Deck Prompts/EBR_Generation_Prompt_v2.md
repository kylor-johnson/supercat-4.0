## DATA SOURCE HIERARCHY — NON-NEGOTIABLE

| Metric | Source | Never |
|--------|--------|-------|
| Revenue, orders, AOV | Postgres `orders` + `extended_price` | Use `orders.total` (inflated) |
| Rep names, attribution | Postgres `orders.rep_first_name + rep_last_name` | BQ as primary |
| Customer names | Postgres `orders.bill_to_company_name` | BQ |
| Feature adoption | BigQuery `mixpanel__events` | Postgres |
| Active users / logins | BigQuery `selected_org` events | Postgres |
| Rep concentration % | Postgres revenue per rep | BQ event counts |

### Rep Attribution Rule
Check GenerationNotes — it will say either:
- `Rep data source: Postgres` — use Postgres rep names throughout
- `Rep data source: BigQuery` — BQ fired reliably, use BQ

If BQ `order_submitted` < 50% of Postgres order count → Postgres wins.
This affects: Top Reps slide, Rep Concentration slide, Rep Activity appendix.

## TTM DATE RULE

TTM = 12 complete months ending on last complete month.
**Never** partial current month. **Never** YTD. **Never** `{year}-01-01`.

March 2026 run = `2025-03-01 → 2026-02-28`
Label everywhere as "TTM" or "Trailing 12 Months". Never "YTD".

## Step 1: Account Classification

### 1A — Deck Type
- **Full deck** = has orders + iPad users → all slides active
- **Engagement-only** = no orders, has BQ events → remove revenue slides
- **Multi-org** = 2+ org shortnames → cross-entity slides active
- **Single-org** = 1 org shortname → adapt cross-entity slides (see rules below)

### 1B — Single Org Adaptations
When account is single org:
- Slide title "Four Divisions, Four Patterns" → "Performance — Trailing 12 Months"
- Slide title "How Your Divisions Compare" → "Feature Usage — Trailing 12 Months"
- Cross-entity rep table → top reps leaderboard for single org
- "Cross-Entity Playbook" slide → "What Good Looks Like" or remove
- Remove all "4 Divisions" language from stats and closings
- No cross-entity rep deduplication needed

### 1C — No Hardcoded Entity Names
**Every** entity name in HTML must come from dynamic config variables.
Search entire output for any of these before delivering — they must not appear:
- Client-specific names from other accounts (Gabby, SC Wholesale, etc.)
- Hardcoded org shortnames in display text

### 1D — Market Calendar Context
Identify Priority 1 events within the TTM window.
Flag inline on every growth metric that overlaps.

## Step 2: Data Mapping

### Slide 3 — Partnership Overview
- Stat row: Entities / Active Users / Orders (TTM) / Revenue (TTM)
- Entity cards: one per org with users, orders (TTM), revenue (TTM)
- Framing: neutral and observational. Never "first time we've..."
- All stats labeled TTM

### Slide 4 — Platform Coverage
- Module matrix: entities as rows, features as columns
- Only show features in the account's active subscription
- Gap cells only for features that are activated but unused
- Footnote any gap that is intentional by design

### Slide 5 — Opening Discovery
- 3 questions (not 5) before data is shown
- At least 1 anchored to a specific data point
- At least 1 referencing a market calendar event
- Question 3: "What would make this conversation most valuable today?"

### Slide 6 — Platform Impact (Hero)
- 4 stats: Revenue (TTM) / Transactions (TTM) / Active Users / Adoption Rate
- One insight line with specific behavioral stats (logins, searches, etc.)
- Market calendar flag if TTM includes Priority 1 event

### Slide 7 — Entity Performance + Growth
- Cross-entity table: Orders TTM / Revenue TTM / AOV / Recent Growth / Self-Service %
- Growth % rules:
  - Check every % against market calendar
  - Overlaps Priority 1 → add `[Market-Driven]` tag
  - Decline after Priority 1 period → label `[Post-Market Normalization]`
  - Never show red decline card without market calendar annotation
- Growth cards: only positive growth entities

### Slide 8 — Sales Team Intelligence
**Section A — Adoption table:**
- Licensed / Active / Active % / Orders / Revenue per entity
- Licensed = from Postgres with correct filter (reps only)
- Active = from BigQuery `selected_org` events

**Section B — Top Reps:**
- Source: check GenerationNotes for rep attribution source
- If Postgres → rank by `orders.rep_first_name + rep_last_name` revenue
- If BQ → rank by `order_submitted` events per username
- Columns: Rep / Orders / Revenue / Customers / Breadth

**Section C — Rep Concentration:**
- Always from Postgres revenue per rep, never BQ
- Thresholds: <10% Low (green) / 10-19% Moderate (gold) / ≥20% High (red)
- 20% threshold footnote required

### Slide 9 — Feature Intelligence
- Heavy Adoption (left) vs Zero/Near-Zero (right)
- Full benchmarking heatmap table
- Only show zero-usage features that ARE in the subscription
- Heatmap: cell value ÷ row max for color intensity
- Leader column = entity with row maximum

### Slide 10 — Customer Intelligence
- Active customers / ordering customers / AOV / top concentration per entity
- Name the top customer and dollar amount (not just %)
- Green callout: reactivation opportunity
- Gold callout: concentration flag if >5%

### Slide 11 — Data-Anchored Discovery
- 5 questions tied to specific data points shown
- Any growth citation must name the market event if applicable

### Slide 12 — Growth Opportunities
- Max 3 recommendations from actual data gaps
- Each: GAP (from data) / PATH (specific actions) / OUTCOME (business result)
- Only triggered signals — don't recommend features not in subscription
- Note optimal timing relative to market calendar

### Slide 13 — Feature Roadmap
- Only features in active subscription that are unused or underused
- Status pills: Pilot Ready (gold) / Active (green) / Not Started (red)

### Slide 14 — Housekeeping + Next Steps
- Open tickets / Payment status / Data health / Engagement cadence
- Use actual data from GenerationNotes — no generic placeholder text
- Two-column commitments: ours (timelines) / theirs (open-ended)

### Slide 16 — Closing
- Format: "[N] Users. [N] Divisions. $[X]M Trailing Twelve Months."
- Never YTD in the closing stat
